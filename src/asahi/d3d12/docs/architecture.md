# d3d12agx architecture

## The stack

```
   application / game / conformance suite
        │  D3D12 COM ABI (ID3D12Device, ID3D12GraphicsCommandList, …)
        │  headers: microsoft/DirectX-Headers (MIT) + winadapter.h
        ▼
   d3d12agx.dll (Windows) / libd3d12agx.so (Linux)
        │                                           ← src/asahi/d3d12/
        │        reuses, unmodified where possible:
        ├─ src/asahi/lib      agx_device / agx_bo / VA / submit
        ├─ src/asahi/layout   image/tiling/compression layouts (ail)
        ├─ src/asahi/genxml   hardware packet packing (agx_pack)
        ├─ src/asahi/compiler NIR → AGX ISA backend
        ├─ src/asahi/libagx   internal GPU helper kernels
        └─ src/compiler/nir   the IR everything meets in
        ▼
   platform backend
        ├─ Linux:   /dev/dri/renderD* through drm/asahi
        └─ Windows: D3DKMT allocation, VA, residency, submit and fences
```

The D3D12 object model is implemented directly — COM vtables in plain C
structs, the way vkd3d-proton does it — but the backend of every object is
the same AGX substrate Honeykrisp uses, **not** Vulkan calls.

**Honeykrisp (`src/asahi/vulkan/hk_*`) is the worked example** of driving
this GPU from a modern explicit API: queue submission (`hk_queue.c`), command
encoding (`hk_cmd_*.c`), memory (`hk_device_memory.c`), meta operations
(`hk_cmd_meta.c`, `agx_bg_eot.c`). Read it as the map from API concept →
hardware mechanism, then express the D3D12 version of that concept against
the same `agx_*` layer. When a hardware question comes up, the answer comes
from the Asahi/Mesa tree or from measurement on real hardware — never from
guessing at register semantics.

## Consequences of the substrate

- **Memory:** Apple silicon is UMA. All heaps use the same physical memory
  domain and `Map()` never needs a staging dance. Private resources use the
  platform's ordinary `agx_bo` allocation path. On Windows, shareable
  resources and heaps are D3DKMT resources from creation onward, rather than
  private allocations copied into shareable storage later.
- **Sync:** D3D12 fences have timeline semantics. Linux maps them to DRM
  syncobj timelines. Windows maps shared fences to D3DKMT monitored fences;
  those same objects are usable by CPU waits, AGX queue submission and other
  D3D processes through NT handles.
- **Queues:** DIRECT/COMPUTE/COPY all target asahi submit queues; the
  hardware distinction that matters is render vs compute encoders.
- **Presentation stays outside this API driver.** On Windows, the Triton
  D3D11 UMD remains the WDDM/DXGI desktop and presentation driver. Native
  D3D12 applications hand it the same D3DKMT resource and monitored fence,
  so presentation does not require a second allocation or a blit.

## Windows process boundary and zero-copy handoff

`d3d12agx.dll` is an application-facing native D3D12 implementation. It is
not a WDDM D3D12 UMD/DDI and does not replace the D3D11 display stack. Apps
opt in through the normal D3D12 API; device creation and command submission
then go straight to AGX through the D3DKMT platform backend.

The bridge to DXGI/D3D11 consists of standard shared-object operations:

1. A resource created with `D3D12_HEAP_FLAG_SHARED` is born as a shareable
   D3DKMT resource. Its runtime-private data carries the wire-compatible
   D3D12 descriptor and D3D11 texture prefix needed by either consumer.
2. `CreateSharedHandle` exports that resource as an NT handle.
   `OpenSharedHandle` imports and adopts the same KMD allocation; it never
   allocates replacement storage or copies pixels.
3. A `D3D12_FENCE_FLAG_SHARED` fence is a shareable D3DKMT monitored fence.
   The producer signals the final render value and the presentation consumer
   waits for that same value before scanning out or composing the resource.
4. Named handles, security descriptors, inheritance and explicit residency
   are translated only in `d12_platform_windows.c`. Linux keeps its DRM
   allocation and sync paths, and unsupported Win32 sharing entry points stay
   isolated as `E_NOTIMPL` stubs there.

This is the zero-copy contract: one KMD allocation, one shared timeline, and
two API views. Swapchain policy and desktop ownership remain with DXGI/D3D11.

## The shader path

Shaders arrive as DXIL (SM 6.x, DXC output) — frozen LLVM 3.7 bitcode plus
metadata. The design constraint is deliberate and absolute:

> **No SPIR-V anywhere in the pipeline.** Not as an intermediate, not for
> internal shaders. DXIL is translated straight to NIR.

Verified at the binary, not just asserted: `libd3d12agx.so` and the
standalone tool contain **zero** SPIR-V parser symbols (`spirv_to_nir`,
`vtn_build`, `nir_to_spirv`), link no SPIR-V or Vulkan library, and none of
this driver's own object files reference SPIR-V at all.

One inherited detail, so it does not read later as a contradiction: the
binary does contain `vtn_bindgen_dummy`, from Mesa's autogenerated
`libagx.cpp`. `src/asahi/libagx` holds AGX helper kernels written in OpenCL
C, which **Mesa's build** compiles through SPIR-V and then runs
`vtn_bindgen2` over to emit binding code — the same for Honeykrisp and the
Gallium driver. This driver uses those precompiled helpers
(`d12_list_dispatch_precomp`, the copy kernels), but that is build-time
substrate machinery: no SPIR-V exists at run time, and no application shader
ever passes through it.

`src/asahi/d3d12/dxil/` contains a self-contained implementation:

| file | role |
|---|---|
| `d12_dxil_bitstream.c` | DXBC container + LLVM bitstream reader |
| `d12_dxil_module.c` | bitcode → types, constants, metadata, functions |
| `d12_dxil_nir.c` | DXIL ops → NIR (the bulk of the work) |
| `d12_dxil_compile.c` | standalone tool: DXIL in, AGX disassembly out |

Internal/meta shaders use Mesa's native NIR builders exactly as `agx`/`hk`
meta code does.

DXBC (SM ≤ 5.1, FXC output) is a later, separate frontend — the format is
fully publicly documented.

### The binding model

Resource bindings are assigned dense **slots** from the root signature. A
shader's `createHandle`/`createHandleFromBinding` resolves to its slot; the
address arithmetic happens at the access site. Three handle flavours exist,
distinguished in `handle_info()`:

1. **Range handles** — index one of three arrays of 64-bit values in GPU
   memory: resource addresses, UAV counter addresses, and buffer-view counts.
   A two-level header of two pointers per level is published in a reserved
   uniform register. Plane selection therefore uses vector channels rather
   than large AGX global-load immediates.
2. **Dynamic handles** — the same, with a computed slot. Stride and kind come
   from the range's base slot, valid because a range shares one
   `dx.resources` record.
3. **SM 6.6 heap handles** (`ResourceDescriptorHeap[i]`) — the def is a raw
   heap index into the shader-visible heap's `struct d12_descriptor` array
   **in memory**. That layout is therefore ABI: `address` at offset 0,
   `counter_address` at offset 8, asserted in `d12_private.h`.

Textures are not reachable by address: AGX reads a hardware descriptor, so
the command list builds a texture heap from the root table and publishes it
in a uniform. Samplers are different again — the backend's sampler operand
indexes **sampler state registers** loaded by the USC SAMPLER word, not a
heap. See `docs/findings.md`, which records how that was established.

Reserved uniform registers (see `dxil/d12_dxil.h`):

| uniform | contents |
|---|---|
| `D12_UNIFORM_ROOT` | address of the root table (non-fragment stages) |
| `D12_UNIFORM_FRAGMENT_ROOT` | address of the root table after the fragment ABI's reserved EMRT/blend registers |
| `D12_UNIFORM_TEXTURES` | address of the texture descriptor heap |
| `D12_UNIFORM_HEAP` | address of the SM 6.6 shader-visible heap |

`reserved_preamble` is set to `D12_UNIFORM_RESERVED` so the compiler's
preamble allocates above them.
